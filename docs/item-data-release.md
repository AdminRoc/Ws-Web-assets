# Item Data Release Contract

`Ws-Web/data/**` contains two different classes of files:

- Manually maintained leaderboard source records. These files are not item-pipeline inputs and must never be rewritten, reformatted, deleted, or regenerated by item-data workflows.
- Item artifacts under `Ws-Web/data/item/**`. These are the only `Ws-Web` files this release contract may read and mirror.

The contract is declared in `item-artifact-contract.json`. The synchronizer reads only declared source paths from `Ws-Web` and writes only this repository's mirrors/release metadata. The validator compares the private `Ws-Web` item artifacts with the public `Ws-Web-assets` mirror and reports missing files, JSON errors, hash mismatches, duplicate keys, and values that exceed the documented 1 MB EdgeOne KV limit.

Release hashes and byte counts are calculated from canonical LF bytes, matching the committed/public files on GitHub. The synchronizer treats CRLF and LF checkouts as the same artifact, avoiding Windows-only dry-run diffs and mismatched release metadata.

The produced `data/item/wm-items.json` includes Warframe.market's unique `id`. That `id` is the cross-run identity; `slug` is a mutable URL label and may change. A one-time migration from pre-ID artifacts accepts only a unique exact English-name match. Normal item order requests should use `/v2/orders/itemId/{id}`; keep `slug` for display and outbound market links.

The public producer Actions live in `Ws-Web-assets`: `build-wm-data.yml` produces `wm-items.json` and `drops-index.json`, while `harvest-wm-items-i18n.yml` produces the append-only `item-i18n-harvest.json` (including the weekly official-localization pass). They check out private `Ws-Web` and the pinned private Core scripts, validate stable identities/history, preserve original bytes when the semantic output is unchanged, and stage only their explicitly allowed `Ws-Web/data/item/**` source paths. After a real source commit they dispatch `sync-item-kv.yml`; that separate publisher reads only declared contract artifacts, updates the public Assets mirror, validates the release, and publishes the size-eligible values to `ITEM_KV`. The legacy `harvest-item-i18n.yml` is a manual alias to the public translation producer. None of these item jobs may touch leaderboard sources or other `Ws-Web` data. Other legacy Assets workflows that still write outside the item contract remain disabled until each has a verified owner, output scope, and consumer map.

`item-release.json.release_id` is the first 40 hexadecimal characters of SHA-256 over the canonical release identity (schema, source repository, release path, and complete artifact descriptor/hash set). It changes only when the declared artifact release changes—not for unrelated Ws-Web code or workflow commits. The full SHA-256 remains recorded for every artifact. This keeps browser cache keys/release markers content-aligned and avoids pointless Assets commits, ITEM_KV marker writes, and linked Maker builds.

Before each KV PUT, `sync-item-kv.yml` reads the current value with a cache-busting query and skips the write only when its bytes exactly match the expected artifact. A failed read other than a real 404 aborts before writing. After a PUT it reads the value back and verifies the exact SHA-256; `item_release_meta` remains the final readiness marker. Before publication the workflow also checks that both deployed item pages load the same release-loader URL and that the loader contains the KV/artifact mismatch and missing-hash guards. `Ws-Web-item` commit `15c5e31` implements that protocol: it uses ITEM_KV only when bytes match the release descriptor and falls back to the exact pinned Assets revision on mismatch; when a valid marker omits an artifact hash, it fails closed instead of accepting unverified bytes. A legacy fallback remains only when the release marker itself is unavailable.

Current publication target:

```text
EdgeOne project: wfspeed-item
KV binding: ITEM_KV
KV namespace: item_data
Read endpoint: https://item.wfspeed.run/api/kv?key=<key>
Write endpoint: https://item.wfspeed.run/api/update-kv
```

All item artifacts are plaintext JSON. The documented EdgeOne per-value limit is 1 MB. `drops-index.json` is therefore declared `assets-only`; `Ws-Web-item` validates `item_release_meta` against the matching `item-release.json`, pins its public Assets fallback to `assets_revision`, and loads the drop index outside KV.

The main-site static copies at `https://wfspeed.run/data/item/` are a separate Tencent EdgeOne Maker publication path. The tracked `Ws-Web/edgeone.json` and `_headers` configure these static routes and their cache behavior. This same-origin publication is distinct from the public Assets/jsDelivr fallback and the `Ws-Web-item` `ITEM_KV` channel; retaining one does not replace the others. The old Tencent CDN purge helper is unrelated historical residue, not the Maker build/cache service and not evidence of deployment or cache convergence. The user reports that linked Maker projects rebuild on each push, so both a changed private `Ws-Web` source commit and a changed public Assets mirror commit may consume build capacity. Actions must therefore suppress timestamp/format-only commits, batch only semantically changed artifacts, and verify live hashes after the relevant Maker build; a Git push alone does not prove deployment.

The item-index builder must preserve WM identity by stable `id`, not `slug`. The official drop-index builder must not silently reset a malformed previous baseline or remove previously published item/source relationships; a confirmed removal requires a reviewed baseline change. These guards are in the private Core revision `3606522cea52b15ee028bfb35de0d98e4892c054`, pinned by the public Assets producer workflows. The latest validated upstream release contained 3,892 unique stable-ID items and 2,750 drop-index entries with no prior slug, item key, or source-row loss.

No automated workflow may delete item artifacts or leaderboard source records during the release migration. Old KV keys will be retired manually only after the new release reader has been deployed and verified.
